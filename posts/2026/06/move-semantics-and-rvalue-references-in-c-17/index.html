Move Semantics and Rvalue References in C++17

Introduction

Modern C++ (since C++11 and beyond) provides move semantics and rvalue references as powerful features to improve the efficiency of object handling. These features address the performance pitfalls of traditional copy semantics by allowing us to transfer resources between objects rather than always duplicating them. In my experience, this has drastically reduced the overhead of passing and returning large objects, and it simplifies ownership management in complex systems.

In this post, I explain what move semantics and rvalue references are, how they work in C++17, and how they optimise resource management and improve performance in real-world code. I also walk through examples of defining move constructors and move assignment operators, using an analytical approach to illustrate their benefits. Throughout, I draw on authoritative sources and practical observations to show why embracing move semantics is essential for intermediate and advanced C++ developers.

The Cost of Copying and the Need for Moves

Before move semantics, copying objects was often the only way to transfer data, which could be expensive for resource-heavy objects. A copy operation typically entails allocating new memory and duplicating the contents of the source object. For example, consider a class managing a dynamic array of integers: a copy constructor would allocate a new array and copy every element, a costly procedure for large arrays. Such deep copies not only consume CPU time, but also may fragment memory or exhaust resources if done excessively.

A notable pain point was returning large objects by value. In C++98, returning a std::vector or other large container could invoke multiple copy operations: one to create a temporary return value and another to copy it into the caller, only to then destroy the temporary. Although compilers could sometimes elide copies, many scenarios still incurred needless copying overhead.

Move semantics were introduced to tackle this inefficiency. The core idea is straightforward: if an object is about to be destroyed or is a temporary rvalue, transfer ownership of its resources to the target instead of cloning them. In other words, move the resource rather than copy it. This approach avoids allocating new memory or duplicating data. The source is left in a safe but otherwise indeterminate state and can be destroyed or reassigned without affecting the moved resource.

Importantly, the program’s logic remains correct. We have not created new data, but simply reused the existing data in a new location.

Understanding Rvalue References

Move semantics in C++ are enabled by rvalue references, a new kind of reference introduced in C++11. To understand their role, it helps to recall the concept of value categories in C++:

  • Lvalues are expressions that have a persistent address in memory. They represent a specific location, and you can take the address of an lvalue with the & operator. Variables and named objects are lvalues.
  • Rvalues are temporary values or objects that do not have a persistent memory address accessible to the program. They typically arise from literals or temporary objects returned by functions. They are ephemeral and will be cleaned up soon, such as the result of x + y or a function returning a new object.

In pre-C++11 code, one could bind a const lvalue reference to a temporary, for example const T& temp = T();, but that did not allow modifying the temporary. C++11 introduced rvalue references, denoted by &&, which can bind to temporaries and allow modification of them.

An rvalue reference is essentially a reference that explicitly targets rvalues. This new reference type is the linchpin of move semantics: it lets us distinguish in function overloading and class interfaces whether a parameter is a transient object that we can safely pilfer resources from. If a function has two overloads, foo(const T&) and foo(T&&), calls with lvalues will match the former, whereas calls with rvalues or explicitly moved lvalues will match the latter. That distinction enables optimal handling for temporaries.

A quick illustration of rvalue references in action:

std::string s1 = "Hello ";
std::string s2 = "World";
std::string&& temp = s1 + s2;  // s1 + s2 produces a temporary (rvalue)
temp += "!";                   // Modify the temporary through an rvalue reference
std::cout << temp << "\n";     // Outputs "Hello World!"

In the snippet above, s1 + s2 creates a temporary std::string containing "Hello World". We bind this temporary to std::string&& temp. Unlike an lvalue reference, an rvalue reference to a temporary allows us to modify it even though it has no name of its own in the program’s original code.

We successfully append "!" to the rvalue via temp. This would not be possible with a regular const std::string& binding, which is read-only. While this ability to manipulate temporaries might seem like a curiosity, it paves the way for implementing move operations that efficiently transfer resources from these short-lived objects.

std::move and Casting to Rvalue

How do we trigger move semantics on an object that we have an lvalue for, meaning a named variable? This is where the utility function std::move comes in. Despite its name, std::move does not move anything by itself. It is a cast that converts an lvalue into an rvalue reference, signalling that we are treating this object as a temporary that can be safely pilfered.

For example:

std::string a = "Large string...";
// std::string b = a;           // Would invoke copy constructor (a is lvalue)
std::string b = std::move(a);   // Invokes move constructor, transferring data

After this code, b obtains the contents that originally belonged to a, and a is left in an empty but valid state. The expression std::move(a) yields an rvalue reference to a, allowing the move constructor of std::string to be called.

Without std::move, the assignment b = a would have called the copy constructor, making a full duplicate of the string data. By contrast, b = std::move(a) calls the move constructor, which typically just swaps pointers or lengths and nulls out a’s data pointer instead of copying characters. This is far cheaper, especially for large strings or containers.

It is important to note that after moving, we should not use a in any way that depends on its old contents. It is essentially an empty shell now. But we can assign a new value to a or let it go out of scope safely, because the move constructor guaranteed that a’s state is harmless.

Implementing Move Constructors and Move Assignment Operators

To take full advantage of move semantics in our own classes, we need to implement a move constructor and a move assignment operator. These are special member functions, analogous to the copy constructor and copy assignment operator, but they accept an rvalue reference to the class type. Their job is to transfer the internal resources from the source object to the target object.

Consider a minimal dynamic array class managing an integer buffer:

#include <algorithm>
#include <iostream>
#include <utility>

class MyArray {
public:
    // Constructor: allocate resources
    MyArray(size_t length)
        : length(length), data(new int[length]) {
        std::cout << "Constructing MyArray of size " << length << "\n";
    }

    // Copy constructor: deep copy resources
    MyArray(const MyArray& other)
        : length(other.length), data(new int[other.length]) {
        std::copy(other.data, other.data + length, data);
        std::cout << "Copying MyArray of size " << length << "\n";
    }

    // Move constructor: steal resources from rvalue
    MyArray(MyArray&& other) noexcept
        : length(other.length), data(other.data) {
        other.length = 0;
        other.data = nullptr;
        std::cout << "Moving MyArray of size " << length << "\n";
    }

    // Copy assignment: deep copy resources
    MyArray& operator=(const MyArray& other) {
        if (this != &other) {
            delete[] data;  // free existing data
            length = other.length;
            data = new int[length];
            std::copy(other.data, other.data + length, data);
        }
        std::cout << "Copy-assigning MyArray of size " << length << "\n";
        return *this;
    }

    // Move assignment: transfer resources from rvalue
    MyArray& operator=(MyArray&& other) noexcept {
        if (this != &other) {
            delete[] data;  // free current resource
            length = other.length;
            data = other.data;
            other.length = 0;
            other.data = nullptr;
        }
        std::cout << "Move-assigning MyArray of size " << length << "\n";
        return *this;
    }

    // Destructor: release resources
    ~MyArray() {
        delete[] data;
        std::cout << "Destructing MyArray of size " << length << "\n";
    }

private:
    size_t length;
    int* data;
};

In this code, MyArray manages a raw heap-allocated array through data. We provide:

  • A copy constructor that performs a deep copy of the array.
  • A move constructor that takes MyArray&& and steals the pointer and length from other, then nullifies other.data to avoid double deletion.
  • A copy assignment operator that also does a deep copy after freeing existing data in the target.
  • A move assignment operator that frees current data and then appropriates other’s data pointer, again setting other.data = nullptr to relinquish ownership.
  • A destructor that frees the allocated memory, if any.

We mark the move constructor and move assignment operator as noexcept. This is a best practice because standard containers such as std::vector rely on that guarantee to safely move elements during reallocation. If a move constructor might throw, some container operations will fall back to copying instead to preserve strong exception safety. Typically, move operations should be written in a way that they cannot fail, since they usually just swap pointers and set nulls.

Now consider how the class behaves in practice:

MyArray a(5);
MyArray b = a;            // Uses copy constructor
MyArray c = std::move(a); // Uses move constructor
MyArray d(5);
d = c;                    // Uses copy assignment
d = std::move(b);         // Uses move assignment
  • MyArray b = a; invokes the copy constructor. A new allocation occurs and the data is copied.
  • MyArray c = std::move(a); invokes the move constructor. Instead of allocating new memory, c takes over a’s buffer. After this, a is still valid, but effectively empty.
  • d = c; calls copy assignment to duplicate c’s data into d.
  • d = std::move(b); calls the move assignment operator, transferring b’s data to d. After this, b becomes an empty shell, and d now owns the data.

Observing the sequence of operations makes it clear how moves avoid unnecessary work. Every time we move instead of copy, we save an allocation and a bulk copy of data. The savings become far more significant with larger buffers, where copying could mean millions of elements. Moves simply adjust a few pointers and integers, a constant-time operation.

Because we delete any old data in the target and nullify the source, we maintain proper resource ownership without leaks or double-free errors.

The Rule of Five

One important guideline in modern C++ is the Rule of Five, an extension of the classic Rule of Three. It states that if your class needs any custom special member function to manage resources, such as a destructor, copy constructor, or copy assignment operator, it likely needs all of the following:

  • Destructor
  • Copy constructor
  • Copy assignment operator
  • Move constructor
  • Move assignment operator

In the MyArray example above, we defined all five. Following this rule helps ensure that your class handles copy and move semantics correctly and safely. If you neglect to implement move operations in a class that owns a resource, you may end up with inefficient code that falls back to copies, or even subtle ownership bugs.

Conversely, if a class can rely on compiler-generated special member functions, the Rule of Zero suggests defining none of them and letting the compiler do the work. But for classes managing raw resources, being explicit and following the Rule of Five is the robust approach.

Performance and Resource Management Benefits

By now, it is evident that move semantics can eliminate a lot of redundant copying. The most important performance and resource-management benefits show up in a few recurring scenarios.

Returning Large Objects from Functions

In older C++ standards, returning a large object such as a std::vector or std::string by value could be expensive. With move semantics, the returned temporary can be moved into the caller instead of copied, significantly reducing overhead.

In fact, C++17 goes even further by guaranteeing copy elision in many return scenarios. The object is constructed directly in the caller’s space with no copy or move at all. This means writing functions that return large containers by value is now not only convenient, but also efficient. You get essentially zero-cost transfer of large results thanks to moves and copy elision combined.

Transferring Ownership of Resources

Move semantics shine when an object holds a resource such as memory, a file handle, or a socket and you want to transfer that ownership. A prime example is std::unique_ptr. A unique_ptr cannot be copied, because that would duplicate ownership of the heap object. But it can be moved, transferring the ownership safely:

std::unique_ptr<Foo> p1 = std::make_unique<Foo>();
auto p2 = std::move(p1);

After this, p2 owns the Foo and p1 becomes nullptr. No memory was copied; only ownership was transferred. This pattern is far safer and clearer than manually managing raw pointers.

Many modern C++ patterns use move-only types such as std::unique_ptr and other RAII wrappers to represent exclusive ownership of resources, relying on move semantics to transfer that ownership when needed. In practice, move-only types force clearer thinking about ownership, and std::move makes ownership transfer explicit, efficient, and semantically clean.

Optimising Container Operations

The C++ standard library containers have been retrofitted to take advantage of move semantics. When you insert elements into a container or resize it, the container will prefer moving elements if it can.

For example, when a std::vector<T> grows and needs to reallocate its storage, it will move each element of type T into the new storage if T has a move constructor that is noexcept. This is much faster than copying each element, especially if T holds large data or is non-trivially copyable.

Another example is std::vector::push_back, which has an overload that takes T&&. If you call v.push_back(std::move(x)), it can use T’s move constructor to construct the new element efficiently. Standard algorithms such as std::swap also rely heavily on move operations.

Overall, the STL ensures that your code benefits from moves automatically in C++11 and later. To maximise performance, however, you should enable moves for your own types and use std::move when you intentionally want to transfer resources from named objects.

Avoiding Temporary Allocations and Redundant Destruction

A more nuanced benefit is that moving often results in fewer allocations and deallocations overall. A moved-from object often does not need to free its resource in its destructor because the resource was passed on.

For instance, when we moved a into c in the earlier MyArray example, a’s destructor found data == nullptr, so it did nothing. Likewise, c did not allocate new memory when it took ownership of the existing pointer. Fewer allocate and free operations means less work for the memory allocator and often better cache usage. In high-performance systems, those savings add up.

C++17: Guaranteed Copy Elision and More

Because this discussion is focused on C++17, it is worth noting how C++17 further solidified the efficiency story around moves. C++17 introduced mandatory copy elision in certain situations, which can make even moves unnecessary in those cases.

For example, when you return a local object from a function, the compiler is required in many cases to construct that object directly in the caller’s storage without invoking either a copy or move constructor. This was an optimisation compilers often performed anyway through return value optimisation (RVO) and named return value optimisation (NRVO), but in C++17 parts of that behaviour are guaranteed by the language.

The practical effect is that you can write functions that return big objects and trust that no superfluous copying or moving will occur when guaranteed elision applies. The object materialises directly in the destination.

Does this make move constructors less important? Not really. Copy elision covers specific scenarios, such as returning objects, but move semantics remain crucial for all the other cases: passing function arguments, handling intermediate results, transferring ownership, and container operations that cannot always be elided.

A common question is: if C++17 elides copies, why bother with move constructors at all? The answer is that return value optimisation only handles some returns, not the general problem of moving objects around. If you insert an existing object into a container with std::move, or if you explicitly want to transfer ownership of something like std::unique_ptr, you still need move semantics.

Another C++17 improvement is that certain uses of temporaries are more straightforward than before. Prior to C++17, even if a temporary could be elided, the object’s class still needed to be movable or copyable in principle because the standard only permitted, but did not require, elision. Since C++17 guarantees elision in specific cases, you can even return some non-copyable, non-movable types from functions. This change underscores how central efficient object transfer has become in modern C++.

Conclusion

Move semantics and rvalue references have revolutionised the way we write high-performance C++ code. By enabling ownership transfer of resources, they eliminate costly deep copies and make resource management more explicit and safe.

In my own development practice, embracing moves has led to cleaner and faster code. Large data structures can be returned or passed around without worry, and resource-owning objects such as smart pointers or custom RAII classes can be designed to transfer ownership with ease. We have seen how to implement move constructors and move assignment operators, and how following the Rule of Five helps our classes behave correctly in a world with move semantics.

Thanks to these features, C++ programs can achieve zero-overhead abstraction goals more effectively. We can write intuitive code, such as returning a big object from a function, and trust that the compiler will do the efficient thing behind the scenes by moving or eliding copies as appropriate.

As we continue into the era of C++20 and C++23, move semantics remain a cornerstone of performant C++ code. Mastering them is essential for any intermediate or advanced C++ developer striving to write robust and efficient systems. In summary, by moving instead of copying, we optimise both runtime performance and resource usage, unlocking the full potential of modern C++ in demanding applications.
